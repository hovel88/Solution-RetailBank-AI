# ADR-001. Итоговое решение по флагману: приоритизация очереди финмониторинга

Статус: предварительное (ожидает пилота)
Дата: 23.11.2026
Инициатива: №1. Автоматически выявлять подозрительные операции по счетам

## Контекст

RetailBank: около 180 тыс. активных клиентов-юрлиц и ИП, 20-25 млн операций/мес. Пороговые правила и внешние сигналы помечают около 35 тыс. операций/мес; служба финмониторинга (25 сотрудников) разбирает около 10 тыс. операций/мес, очередь растёт, приоритет отдается крупным суммам.

Эффект — рост результативности проверок при том же штате, а не сокращение штата.

Ссылки: паспорт (разделы 1-5), ADR v0.1 (Task 2), TCO, план пилота.

## Жёсткие ограничения

- **115-ФЗ и ПОД/ФТ** — обязанность банка, а не инициатива бизнеса. Решение встраивается в правила внутреннего контроля и не отменяет установленной процедуры выявления и фиксирования операций.
- **Банковская тайна и ПДн** (клиенты, представители, поручители). Правовое основание, договор с обработчиком, регион обработки и хранения — это к комплаенсу, DPO и юристам.
- **Автоматизированные решения по ПДн**, затрагивающие права субъекта, — только при условиях, установленных законом, с правом возражения. Вопросы по применимости также к юристам.
- **Решение о блокировке/отказе** принимает человек (финмониторинг), а не система. Автоматический вердикт "схема/не схема" в этой постановке недопустим. Кроме того, должна оставаться возможность обжаловать решение.

## Сравнительные критерии

После отсечения по жёстким ограничениям сравниваем по:

- ценность/эффект (рост результативности проверок, удержанные суммы)
- выполнимость (сроки, компетенции, операционная готовность)
- данные (наличие источника сигнала и стоимость его получения)
- стоимость владения (вызовы модели, инфраструктура, ручной контур, поддержка, обновления)
- риск (регуляторный, репутационный, lock на провайдера)

## Рассмотренные варианты

### По данным (путь получения источника сигнала)

| Вариант | За | Против | Почему отклонён или выбран |
| -- | -- | -- | -- |
| Обучение с учителем на исторических эскалациях | Есть готовый след (около 400/мес) | "Эскалация" не значит подтверждённая схема. Обучение воспроизводит логику старых правил. Смещение отбора | Отклонён. Хотя допустим как слабая метка в комбинации |
| Вероятностная контрольная выборка, размеченная экспертами | Несмещённая оценка непроверяемой части потока | Дорого и долго. Нужно выработать гайдлайн и согласованность между экспертами | **Выбран как основной путь** для оценки и накопления меток. Это не первый этап, для т.к. нужно время |
| Разметка силами финмониторинга по гайдлайну | Использует экспертизу службы | Нужна оценка согласованности, есть риск индивидуальных предпочтений | **Выбран** вместе с контрольной выборкой. Это также не первый этап, т.к. тоже нужно время (плюс учесть риск) |
| Постановка без учителя (ранжирование) | Работает без меток, сразу даёт приоритизацию | Не выносит вердикт "схема/не схема". Нужна валидация на контрольной выборке | **Выбран для первого этапа**. Дает только приоритизацию очереди, но это решение быстрее. Классификатор можно прикрутить позже, по мере накопления меток и объема размеченных данных |

**Решение по данным:** на первом этапе — постановка без учителя (ранжирование для приоритизации очереди) + программа сбора меток из двух источников: разобранная приоритетная очередь и постоянная вероятностная контрольная выборка (случайная или стратифицированная по сегментам и суммам). Только очередь брать нельзя — получим новое смещение отбора. Классификатор "схема/не схема" — считаем следующим этапом, когда меток и размеченных данных станет достаточно.

### По размещению

Разведем между собой пилот и прод.

- Пилот — это проверка гипотезы на исторических/обезличенных данных. Ему не нужна боевая инфраструктура, круглосуточная команда и кластер машин с GPU. Ему нужно где-то прогнать модель на данных, которые уже лежат в банке. Исторические данные уже находятся в контуре банка (это его данные). Значит, пилот можно сделать на уже существующей инфраструктуре банка
- Целевой прод — это боевая система на потоке 20-25 млн операций/мес. Вот тут уже нужен выбор: on-prem, своё облако, выделенный контур провайдера или гибрид. Нужно оценить аргументы дорого, долго, есть ли компетенции и т.д.

#### По размещению: Пилот

| Вариант | За | Против | Почему отклонён или выбран для пилота |
| -- | -- | -- | -- |
| Существующая инфраструктура банка | Данные уже в контуре, не нужно строить новый контур, быстро, дёшево | Ограниченные ресурсы, не боевая среда | **Выбран для пилота:** проверка гипотезы на исторических/обезличенных данных без строительства отдельного ИИ-контура |
| Публичный API | Дёшево, быстро | Чувствительные данные (банковская тайна, ПДн) уходят в мультиарендный контур | Отклонён. Для пилота на обезличенных данных технически возможно, но создаёт лишний риск и вопросы к DPO. Риск не оправдан, когда есть своя инфраструктура |
| Выделенный контур провайдера | Изоляция, SLA | Дороже, чем использовать существующую инфраструктуру | Отклонён. Для пилота избыточен |
| Self-hosting в облаке | Полный контроль, данные не покидают контур | Нужна операционная готовность и компетенции, которых пока нет | Отклонён. Для пилота избыточен |
| On-premises (отдельный ИИ-контур) | Полный контроль, данные не покидают контур | Строится месяцами, дорого, нужна круглосуточная команда | Отклонён. Для пилота избыточен. Гипотезу можно проверить на существующей инфраструктуре |

#### По размещению: Целевой прод

| Вариант | За | Против | Почему отклонён или выбран для прода |
| -- | -- | -- | -- |
| Публичный API | Дёшево, быстро | Данные (банковская тайна, ПДн) уходят в мультиарендный контур. Регион и обучение на данных не гарантируются. | Отклонён. Для прода не подходит по hard constraints |
| Выделенный контур провайдера | Изоляция, договорной SLA, российский контур | Дороже публичного API + зависимость от вендора | Кандидат только для звена LLM (нормализация текста), если оно понадобится |
| Self-hosting в облаке | Контроль, данные в контуре клиента | Нужна операционная готовность и компетенции, которых пока нет | Кандидат на позднюю стадию, когда появится ML-команда эксплуатации и компетенции |
| On-premises | Полный контроль, данные не покидают контур | Долго, дорого, нужна круглосуточная команда | Кандидат для целевого прода при росте нагрузки и наличии команды |
| Гибрид по звеньям | Разные требования у разных звеньев пайплайна | Сложнее эксплуатация | **Выбран для прода:** табличные модели — в контуре банка, LLM (если понадобится) — в выделенном контуре |

**Решение по размещению:**

- **Пилот:** на существующей инфраструктуре банка, на исторических/обезличенных данных, без внешних LLM на чувствительных данных
- **Целевой прод:** гибрид по звеньям. Табличные модели в контуре банка. Если понадобится LLM для свободного текста — выделенный контур провайдера с договорными гарантиями, после ответа DPO и юристов.

### По модели

| Вариант | За | Против | Почему отклонён или выбран |
| -- | -- | -- | -- |
| Публичный рейтинг / флагман | Умная модель | Не отражает поведение на наших данных. Для табличного скоринга избыточна и дорога | Отклонён. Рейтинг не про нашу задачу |
| Классическая ML-модель (градиентный бустинг) на табличных признаках | Стандарт для табличных данных. Дешевле LLM. Предсказуема. Хорошо интерпретируется | Нужны признаки и метки, а на первом этапе меток крайне мало | Кандидат для этапа классификатора. Для ранжирования тоже подходит |
| LLM для нормализации/признаков из назначения платежа | Свободный текст это сильная сторона LLM | Дорого на потоке 20–25 млн операций/мес. Избыточно для извлечения признаков | Кандидат только для звена нормализации текста, но не для всего скоринга |
| Постановка без учителя (ранжирование/аномалии) | Работает без меток, сразу даёт приоритизацию | Не выносит вердикт + нужна валидация | **Выбран для первого этапа** |

**Решение по модели:** на первом этапе — ранжирование на табличных признаках (классическая ML или эвристики + обучение без учителя), с валидацией на контрольной выборке. Применение LLM очень ограничено — только для нормализации свободного текста назначения платежа, если это даст прирост. Классификатор "схема/не схема" это следующий этап, по мере накопления меток, это не первый этап, нужно время.

## Решение

**Запускаем пилот в ограниченном сценарии**, затем — целевой прод при подтверждении допущений.

- **Пилот:** 6-8 недель, на исторических/обезличенных данных, в контуре банка, без внешних LLM на чувствительных данных. Проверяет рост результативности, долю ручной проверки, стоимость на реальном потоке, правовое основание (получить до запуска).
- **Целевой прод:** сервис приоритизации (не классификатор) — ранжирование на табличных признаках; LLM-нормализация текста опционально. Размещение — гибрид по звеньям.
- **Уровень автоматизации:** модель рекомендует порядок, а решение принимает человек. Автоматическое одобрение для флагмана не предусмотрено.

## Экономика

- **TCO за год:** 6 554 240 ₽ (включая резерв 10% на непредвиденное)
- **Стоимость обработки одной проверки:** около 55 ₽
- **Текущий процесс:** 10 000 разборов, около 400 эскалаций на расследование (4%). **1-2 формально подтверждённых схем/мес** (единицы, из кейса)
- **Целевой процесс:** приоритизация не увеличивает число разборов и эскалаций, но повышает долю результативных: **5-10 подтверждённых из 400** (допущение, проверяется пилотом)
- **Прирост подтверждённых:** +3-8/мес (базовый сценарий)
- **Эффект в деньгах зависит от средней суммы удержания X ₽** (в кейсе не указана):
  - при X = 50 000 ₽: +1,8-4,8 млн ₽/год — **не перекрывает TCO** (6,55 млн ₽);
  - при X = 500 000 ₽: +18-48 млн ₽/год — **перекрывает TCO в 3–7 раз**.
- **Дополнительные эффекты (не оценены в деньгах):** снижение жалоб и лишних приостановок, снижение регуляторных издержек, сокращение безрезультатных расследований
- **Стоимость пилота:** порядка 1,1-1,3 млн ₽ (с резервом до 1,6 млн ₽)

## Риски и что с ними делаем

- **Смещение отбора**: контрольная выборка + оценка по сегментам. Нельзя обучать только на очереди.
- **Утечка из будущего**: не использовать "эскалировано" и "исход расследования" как признаки. Это данные из будущего по операции.
- **Регуляторный риск**: правовое основание, автоматизированные решения по ПДн. Нужно получить ответ юристов и DPO ещё до запуска.
- **Ложные блокировки**: человек в петле, guardrails, обязательно оставить возможность апелляция.
- **Lock на провайдера**: реализовать адаптер перед провайдером.
- **Ошибка прогноза эффекта** — пилот проверяет главное допущение (рост результативности); при провале проект закрывается, потери ограничены стоимостью пилота.

## План выхода

Реализовать адаптер перед LLM-провайдером (если используется), это позволит вносить меньше изменений в систему и легче пережить смену провайдера.

Производим миграцию на другого провайдера или self-hosting решение при изменении цен, условий или появлении open-weight-модели, укладывающейся в требования. Табличные модели применяем свои, зависимости от вендора тут нет.

## Триггеры пересмотра

- изменение законодательства (115-ФЗ, ПДн)
- появление достаточной разметки для классификатора
- изменение цен или условий у LLM-провайдера
- рост нагрузки или изменение профиля операций
- провал пилота по критериям остановки
- существенное отклонение фактического TCO от расчётного (например, безопасность/инфраструктура дороже более чем на 50%).

## Рекомендация бизнесу

**Запускать пилот, но!**

Пилот стоит 1,1-1,3 млн ₽ (с резервом до 1,6 млн ₽) и отвечает на два вопроса, от которых зависит окупаемость:

1. **Даёт ли приоритизация измеримый прирост обоснованных эскалаций** (допустим, сейчас 1-2 подтверждённых из 400 эскалаций, а будет 5-10).
2. **Какова средняя сумма удержания X ₽**, от неё зависит, перекрывает ли эффект TCO. При X = 50 000 ₽ и менее — проект не окупается только за счёт удержаний. При X = 500 000 ₽ — окупается в 3-7 раз.

Если пилот покажет, что прирост обоснованных эскалаций есть, а X достаточно велик (или дополнительные эффекты в виде снижения жалоб, регуляторных издержек, — значимы), можем идти далее в прод. Если прирост не подтверждается или X мал и дополнительных эффектов нет — проект закрывается, потери ограничены стоимостью пилота.
