# Паспорт AI-инициативы

## Раздел 1. Триаж

### 1.1. Вердикт по 18 инициативам

Главный вопрос при выборе способа решения задачи: "Обучается ли модель на данных?"

| Инициатива бизнеса | Категория | Комментарий |
| -- | -- | -- |
| 1. Автоматически выявлять подозрительные операции по счетам (транзит, обналичивание, дробление платежей под пороги). | **Гибрид** | Явные нарушения (дробление под порог, дубли, лимиты) — правила.<br>На звене приоритизации нужна обучаемая закономерность по истории проверок. Но меток "схема/не схема" нет, есть три разных по надёжности следа |
| 2. Распознавать и оцифровывать сканы документов, приложенных к кредитной заявке. | **Гибрид** | Распознавание сканов — CV/OCR.<br>Извлечение полей — LLM.<br>Сверка со справочниками и проверка полноты пакета — детерминированный код |
| 3. Чат-бот, отвечающий клиенту, что входит в его тарифный план. | **Гибрид** | Ответ собирается из найденного пункта тарифа (RAG) и данных договора (детерминированный запрос).<br>Для понимания вопроса и формулировки — LLM |
| 4. Прогнозировать годовой уровень просрочки по портфелю кредитов МСБ. | **ML-кандидат** | Нужна закономерность по историческим данным портфеля. Источник сигнала — фактическая просрочка.<br>Однако детали инициативы надо уточнить у бизнеса, т.к. решения могут быть разными |
| 5. Маршрутизировать входящие обращения по нужным отделам. | **Недостаточно информации** | Если клиент выбирает тему в форме — обычная программа (таблица соответствий).<br>Если тема определяется из свободного текста — ML (классификация текста).<br>Вопрос: пользователь выбирает тему сам или её нужно определять из текста? |
| 6. Автоматически проводить платежи на сумму менее 30 000 ₽ без ручного контроля. | **Обычная программа** | Пороговое правило с явным критерием, тут обучаемая закономерность не нужна.<br>Однако такая инициатива уязвима к дроблению под порог.<br>Вопрос: нужны ли накопительные проверки против дробления под порог? |
| 7. Дашборд с разбивкой обращений по регионам и продуктам. | **Аналитика** | Срез прошлого, агрегации, решение принимает человек. По постановке видится, что тут обучаемый прогноз не нужен.<br>Вопрос: нужен ли прогноз нагрузки или достаточно факта? |
| 8. Предсказывать, какие клиенты собираются уйти в другой банк. | **ML-кандидат** | Нужна закономерность по истории поведения. Источник сигнала — факты ухода.<br>Вопрос: что считается "уходом" и за какой горизонт нужен прогноз? |
| 9. Голосовая аналитика звонков в кол-центр (тон, причины обращений). | **Гибрид** | Речь в текст — ASR (обучаемые модели).<br>Классификация тона/темы — ML.<br>Агрегация и отчёты — детерминированный код.<br>Вопрос: категории тона и причин заданы заранее или их надо выявлять из данных? |
| 10. Выявлять поддельные и отредактированные справки о доходах и бухгалтерскую отчётность. | **Гибрид** | Признаки подделки в изображении/метаданных — CV-модель.<br>Сверка цифр с независимыми источниками и арифметические инварианты — код.<br>Вопрос: есть ли история подтверждённых подделок и кто её размечает? |
| 11. Давать клиентам индивидуальные инвестиционные рекомендации по свободным остаткам. | **Заблокировано → уточнить** | ИИК — регулируемая деятельность: договор об инвестиционном консультировании, записи в реестре ЦБ. В текущей постановке запускать нельзя.<br>Нужен ответ юристов и комплаенса: оператор ли банк ИИК, есть ли советник в реестре, допустима ли "информационная" форма (просто дашборд)? |
| 12. Полностью автоматически отказывать в кредите по скорингу, без участия сотрудника. | **Заблокировано → уточнить** | Полный автоотказ затрагивает права субъекта: такие решения допустимы лишь при условиях, установленных законом, с правом возражения.<br>Нужен ответ юристов и DPO. Вероятно переформулировать постановку и добавить человека в петле на спорных случаях |
| 13. Рекомендовать клиенту подходящий продукт банка. | **Недостаточно информации** | "Подходящий" может проходить по правилам соответствия (тогда обычная программа) или по ранжированию по вероятности отклика (тогда ML).<br>Вопрос: что значит "подходящий" — соответствие условиям или прогноз отклика/пользы? |
| 14. Сверять удержанные комиссии по эквайрингу с условиями договора и помечать расхождения. | **Обычная программа** | Детерминированное сравнение чисел по условиям договора. По постановке видится, что обучаемая закономерность тут не нужна |
| 15. Прогнозировать нагрузку на кол-центр для планирования смен. | **ML-кандидат** | Прогноз временного ряда по истории обращений. Источник сигнала — история нагрузки.<br>Вопрос: нужен прогноз по часам/дням/неделям и на какой горизонт? |
| 16. Генерировать PDF-договор на обслуживание из шаблона по данным клиента. | **Обычная программа** | Шаблонизация с подстановкой. Из постановки видится, что LLM не нужна, избыточна и была бы сильно дороже и менее предсказуема |
| 17. Блокчейн для хранения истории операций клиентов. | **Обычная программа** | Не ML-задача, никакой обучаемой закономерность тут не нужно.<br>Вопрос: задача выглядит классической для использования СУБД + аудита, что тут такого особенного, для чего нужен блокчейн? |
| 18. Извлекать финансовые показатели из неструктурированных бухгалтерских документов и банковских выписок. | **Гибрид** | Извлечение полей из текста — LLM.<br>Распознавание сканов — OCR.<br>Нормализация и сверка показателей — код.<br>Вопрос: какие показатели обязательны и есть ли справочник кодов/форм для сверки? |

### 1.2. Полная постановка для трёх инициатив

Постановка заполняется для ML-кандидатов и гибридов. Выбрано три инициативы: №1 (флагман), №2 и №15.

#### Инициатива №1 (флагман). Выявление подозрительных операций

| Поле | Что фиксируем |
| -- | -- |
| **Инициатива без слова «AI»** | Поток операций по счетам → Упорядоченный список операций для проверки финмониторингом |
| **Какое действие изменится** | Приоритизация очереди финмониторинга: те же ~10 тыс. разобранных операций в месяц, но отобранные по риску, а не только по порогу и жалобам |
| **Где именно нужна обучаемая закономерность** | Звено оценки риска и ранжирования: схема определяется сложным сочетанием признаков, которое не описать исчерпывающими правилами.<br>Дробление под порог, дубли, лимиты, накопительные проверки — детерминированный код.<br>Решение о блокировке/отказе — человек |
| **Чего не хватает, допущения** | Нет готовой разметки "схема/не схема". Есть три разных по надёжности следа. Смещение отбора (проверялись только отобранные правилами операции), если что-то не было отобрано это не значит что там всё чисто. Правовое основание и допустимость автоматизированных решений — это к юристам и DPO |
| **Вердикт** | **Гибрид** |

#### Инициатива №2. Распознавание и оцифровка сканов кредитной заявки

| Поле | Что фиксируем |
| -- | -- |
| **Инициатива без слова «AI»** | Пакет документов кредитной заявки (сканы, Excel, фото) → Структурированная карточка полей для андеррайтера |
| **Какое действие изменится** | После обработки получается артефакт с извлечёнными полями со ссылкой на источник вместо ручного переноса. Сокращается время разбора пакета (~полтора часа) и доля ошибок переноса |
| **Где именно нужна обучаемая закономерность** | Распознавание сканов (CV/OCR) и извлечение полей из свободного текста (LLM).<br>Сверка со справочниками, проверка полноты пакета и арифметические инварианты — детерминированный код.<br>Финальное кредитное решение — человек |
| **Чего не хватает, допущения** | Обязательные/опциональные поля. Допустимая доля ручных исправлений. Правовое основание обработки ПДн клиентов, заёмщиков, их представителей и поручителей — это к DPO и юристам |
| **Вердикт** | **Гибрид** |

#### Инициатива №15. Прогноз нагрузки на кол-центр

| Поле | Что фиксируем |
| -- | -- |
| **Инициатива без слова «AI»** | История обращений в кол-центр → Прогноз нагрузки на будущие периоды для планирования смен |
| **Какое действие изменится** | Планирование смен: расписание строится под прогноз, меньше переработок и простоев, лучше соблюдение SLA ответа |
| **Где именно нужна обучаемая закономерность** | Само звено прогноза: закономерность в истории нагрузки (сезонность, дни недели, праздники, эффекты кампаний и т.д.) не описывается простой формулой.<br>Подготовка временного ряда, агрегация, проверка непрерывности — детерминированный код.<br>Утверждение расписания — человек |
| **Чего не хватает, допущения** | Проверить непрерывность и корректность ряда. Учесть сезонность, праздники, выбросы. Определить горизонт прогноза (часы/дни/недели), что повлияет на метрики и рабочую точку |
| **Вердикт** | **ML-кандидат** |
