# Паспорт AI-инициативы

Инициатива №15. Прогноз нагрузки на кол-центр

## Раздел 2. Постановка

| Поле | Что фиксируем |
| -- | -- |
| **Бизнес-действие** | Планирование смен кол-центра под прогноз нагрузки: меньше переработок и простоев, лучше соблюдение SLA ответа |
| **Объект и единица решения** | Период прогноза (час, день, неделя). Одно решение — по одному периоду. Расписание строится на совокупности периодов |
| **Момент** | **Пакетно** (прогноз строится заранее, например, раз в неделю на следующую неделю, раз в день на следующий день) |
| **Операция** | **Прогноз временного ряда** (число обращений на период) |
| **Модальность** | **Временной ряд** (история обращений по часам/дням/неделям) + календарные **признаки** (день недели, праздники) + возможно, внешние **факторы** (кампании, сезонность) |
| **Выход модели** | Прогноз числа обращений на будущий период (число) + интервал неопределённости |
| **Бизнес-выход** | Прогноз нагрузки для планировщика смен, с указанием ожидаемого диапазона (например, "в понедельник 10:00-11:00 ожидается 120–160 звонков"). Отличается от выхода модели: нужна интерпретация и учёт ограничений (доступные сотрудники, SLA) |
| **Источник правильного ответа** | Фактическая история обращений: известно, сколько звонков поступило в каждый период. Появляется по факту, сразу после периода |
| **Конвейер** | Подготовка временного ряда (детерминированный код: агрегация, проверка непрерывности, календарные признаки) → **модель прогноза (обучаемая)** → интерпретация и планирование (код + человек) |
| **Альтернативные постановки** | (1) Прогноз на уровне отдельного оператора — другая задача, другие данные.<br>(2) Прогноз с учётом внешних факторов — сложнее, может быть на поздних этапах.<br>(3) Простое правило, например, "как в прошлую неделю" — это скорее нужно использовать как baseline.<br>**Вопрос бизнесу**: На какой горизонт нужен прогноз (часы/дни/недели) и с какой точностью? От этого будет зависеть метрика и рабочая точка |

## Раздел 3. Оценка качества

| Поле | Что фиксируем |
| -- | -- |
| **Бизнес-метрика** | Соблюдение SLA ответа (доля звонков, отвеченных в целевое время) и доля переработок/простоев |
| **Положительный класс** | **Не применимо**. Это не классификация, для прогноза скорее будет точность прогноза в пределах допустимой ошибки |
| **Метрика под решение** | **MAE** (средняя абсолютная ошибка, на сколько в среднем прогноз отличается от факта, в звонках) и **MAPE** (средняя ошибка в процентах). Ещё можно оценивать долю периодов, где фактическая нагрузка вышла за пределы прогнозного интервала |
| **Baseline** | Простое правило: "нагрузка на следующую неделю = нагрузка на прошлую неделю" или "среднее за последние 4 недели в этот день в этот час". Сравнение по MAE/MAPE и по влиянию на SLA |
| **Проверочная выборка** | Отложенный период (например, последние 3-6 месяцев), не использованный при обучении; покрывает разные сезоны, праздники, выбросы. Оценка на обучающем периоде будет нечестной |
| **Рабочая точка** | Горизонт прогноза и допустимая ошибка: например, MAPE ≤ 15% на горизонте "день" и MAPE ≤ 25% на горизонте "неделя". Значения берется из требований планирования |
| **Показатели в этой точке** | MAE и MAPE на отложенном периоде, доля периодов за пределами интервала, влияние на SLA (если есть исторические данные о расписании) |
| **Цена ошибок** | Недооценка нагрузки — нехватка операторов, рост времени ответа, переработки.<br>Переоценка нагрузки — простои, лишние смены, стоимость работы сотрудников.<br>Недооценка для бизнеса выходит дороже, потому что страдает SLA |
| **Guardrails** | (1) Не растёт доля переработок.<br>(2) Не падает SLA.<br>(3) Не растёт стоимость смен.<br>(4) Прогноз не ломается на праздниках и из-за необычных выбросов. |

## Раздел 4. Готовность данных

| Поле | Что фиксируем |
| -- | -- |
| **Решение** | Прогноз нагрузки для планирования смен |
| **Объект и гранулярность** | Период (час/день/неделя). Запись — один период |
| **Источник и владелец** | История обращений в кол-центр.<br>Владелец: кол-центр и ИТ-команда |
| **Источник правильного ответа** | Фактическая история обращений. Появляется по факту, сразу после периода |
| **Доступность признаков в проде** | Все признаки (история, календарь) доступны в момент прогноза |
| **Разметка** | **Не применимо**. В общем смысле правильный ответ — это факт, он уже есть в истории, размечать нечего. Но нужна проверка корректности временного ряда (непрерывность, отсутствие пропусков, корректность агрегации) |
| **Смещение отбора** | Существует смещение по периодам (например, в праздники мало данных) и по каналам (если часть обращений идёт не в кол-центр) |
| **Репрезентативность** | Нужны разные сезоны, дни недели, праздники, периоды кампаний, выбросы. Если история короткая — прогноз на редкие периоды будет плохим |
| **Объём** | Зависит от истории и горизонта. Для недельного прогноза и прогноза на день нужны разные объемы (больше и меньше данных соответственно) |
| **Качество** | Пропуски в истории, дубли, некорректная агрегация, смена системы записи звонков (может дать разрыв в ряду) |
| **Право использовать** | Агрегированные данные о нагрузке кажется имеют минимальный ПДн, но возможно там есть какая-то банковская тайна. Если в признаки попадают чувствительные данные, лучше получить подтверждение о применимости от DPO и юристов |
| **Вердикт** | **Готово** (при соблюдении проврки непрерывности и качества ряда, покрытия сезонов, праздников и т.д.) |

## Раздел 5. Карточка эксперимента

| Поле | Что фиксируем |
| -- | -- |
| **Где именно теряем** | На праздниках, пиках и выбросах прогноз ошибается, расписание не соответствует нагрузке |
| **Гипотеза причины** | Модель видела мало примеров таких периодов, сезонность и праздники не учтены иил слабо представлены в признаках |
| **Конкурирующие объяснения** | (1) Дело не в модели, а в признаках — календарь не учтён.<br>(2) Дело в качестве ряда — пропуски/разрывы.<br>(3) Дело в горизонте — на неделю точность ниже, чем на день, и это нормально. |
| **Рычаг** | **Признаки** (календарь, праздники, лаги) + **данные** (добрать историю по редким периодам) — на первом этапе.<br>**Модель** можно использовать как рычаг на последующих этапах |
| **Дешёвый различающий эксперимент** | Добавить календарные признаки и лаги, прогнать на отложенном периоде, сравнить MAE/MAPE с baseline. Если прирост есть — гипотеза признаков подтверждается |
| **Ожидаемый эффект** | Снижение MAE/MAPE на праздниках и пиках |
| **Стоимость проверки** | Время ML-команды + инфраструктура |
| **Критерий остановки** | MAE/MAPE не улучшаются после добавления признаков — гипотеза признаков не подтверждается, значит смотреть в сторону качества ряда и горизонт |
