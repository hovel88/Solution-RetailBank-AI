# Паспорт AI-инициативы

Инициатива №1 (флагман). Выявление подозрительных операций

## Раздел 2. Постановка

| Поле | Что фиксируем |
| -- | -- |
| **Бизнес-действие** | Приоритизация очереди финмониторинга: те же ~10 тыс. разобранных операций в месяц, но теперь отобранные по риску, а не только по порогу и жалобам. Цель: рост результативности проверок при том же штате |
| **Объект и единица решения** | Операция по счёту клиента (юрлицо / ИП). Одно решение по одной операции |
| **Момент** | **Пакетно-асинхронно** (операции за период ранжируются и попадают в очередь) + **по запросу аналитика** при разборе конкретного случая (решение принимает человек, а не система) |
| **Операция** | **Ранжирование** (приоритизация очереди) + **классификация** (оценка риска схемы) как вспомогательный сигнал |
| **Модальность** | **Таблица** (сумма, контрагент, ОКВЭД, дата, канал) + **текст** (назначение платежа в свободной форме) + вспомогательные **сигналы** (справочники и внешняя платформа «Знай своего клиента») |
| **Выход модели** | **Число** (оценка риска операции) + упорядоченный **список** операций для проверки + **признаки** (для текста назначения как вход для скоринга) |
| **Бизнес-выход** | Очередь top-N операций для аналитика финмониторинга, с указанием, какие правила/признаки сработали. Не совпадает с выходом модели: в общем случае к выходу модели применяется сортировка, правила и ограничения |
| **Источник правильного ответа** | Три следа разной надёжности: отметка "эскалировано на расследование" (~400/мес), исход расследования, формально подтверждённые случаи (единицы, спустя месяцы). Но ни один не является готовым эталоном |
| **Конвейер** | Детерминированные проверки (дробление под порог, дубли, лимиты, накопительные проверки) → **ML-скоринг и ранжирование** → порог / top-N → ручная проверка → расследование |
| **Альтернативные постановки** | (1) Классификация "схема / не схема" — требует достаточной разметки подтверждённых случаев, которой пока нет.<br>(2) Поиск аномалий (без учителя) — только отмечает нетипичное.<br>(3) Ранжирование для приоритизации (выбранный вариант).<br>**Вопрос бизнесу**: Нужен вердикт по каждой операции или достаточно упорядочить очередь для проверки? |

## Раздел 3. Оценка качества

| Поле | Что фиксируем |
| -- | -- |
| **Бизнес-метрика** | Удержанные суммы на одну проверку (руб./проверка) и результативность проверок (доля проверок, давших подтверждённое нарушение). Сейчас результативна примерно 1-2 подтверждённых из 400 эскалаций (в кейсе формулировка "единицы"); целевой ориентир — рост при том же штате до 5-10 подтверждённых из 400 эскалаций |
| **Положительный класс** | Операция, которая после проверки признана схемой (подтверждённое нарушение). Не "вызывает подозрение", а именно подтверждённая схема |
| **Метрика под решение** | **Precision@N** (доля полезных проверок среди первых N проверенных) и **Recall@N** (доля пойманных схем среди первых N проверенных) при фиксированной пропускной способности (N ≈ 10 тыс. проверок/мес) |
| **Baseline** | Текущий процесс: отбор правилами и жалобами. Сравнение по результативности проверок и удержанным суммам на проверку, с учетом текущего штата |
| **Проверочная выборка** | Вероятностная контрольная выборка операций, размеченная экспертами (по сегментам и суммам) + риск-ориентированная выборка для редких дорогих классов. Проверять на исторических данных нельзя из-за смещения отбора (то что было не отобрано не значит что там всё чисто) |
| **Рабочая точка** | Top-N по оценке риска при N, равном пропускной способности финмониторинга (≈10 тыс./мес). Порог — по оценке операции, оказавшейся на N-м месте |
| **Показатели в этой точке** | Precision@N, Recall@N (по подтверждённым случаям), найденная сумма нарушений среди top-N |
| **Цена ошибок** | Пропуск схемы — риск претензий надзора (за прошлый год два предписания, устранение месяцами, прямые издержки).<br>Лишняя блокировка — остановленный платёж честного клиента (600 приостановок/мес, 450 снимаются, 120 жалоб, часть уходит в другой банк).<br>Пропуск схемы дороже лишней проверки, и хотя это разные вещи, но бизнесу скорее всего будет важен вариант с более высоким recall, даже ценой precision. Но надо подтвердить у бизнеса |
| **Guardrails** | (1) Не растёт доля необоснованных блокировок.<br>(2) Нагрузка на аналитиков не превышает пропускную способность.<br>(3) Сохраняется контроль на редких дорогих схемах |

## Раздел 4. Готовность данных

| Поле | Что фиксируем |
| -- | -- |
| **Решение** | Приоритизация очереди финмониторинга (ранжирование), а не вердикт "схема / не схема" |
| **Объект и гранулярность** | Операция по счёту. Запись — одна операция |
| **Источник и владелец** | История операций (несколько лет) + справочники тарифов и лимитов + сигнал внешней платформы "Знай своего клиента".<br>Владелец: ИТ-команда банка и служба финмониторинга (по разметке) |
| **Источник правильного ответа** | Три следа: отметка "эскалировано" (около 400/мес), исход расследования, формально подтверждённые случаи (единицы, спустя месяцы) |
| **Доступность признаков в проде** | Все признаки (сумма, контрагент, ОКВЭД, дата, канал, назначение платежа, история) доступны в момент решения. Отметка "эскалировано" и исход расследования **недоступны** для новой операции (это будущее) |
| **Разметка** | Подтверждённых случаев для обучения с учителем недостаточно. Нужна программа сбора: вероятностная контрольная выборка + разметка силами финмониторинга по выработанным правилам при согласованности между разметчиками |
| **Смещение отбора** | Главная **проблема**. Метки есть только у операций, отобранных пороговыми правилами и внешними сигналами. Непроверенная операция не равна чистой операции. Обучение на исторических проверках воспроизводит логику старых правил. Оценка на такой выборке не описывает реальную работу системы |
| **Репрезентативность** | Нужны сегменты по типам клиентов (юрлица/ИП, ОКВЭД), суммам, каналам, регионам; отдельно — редкие дорогие схемы. Новая история (новые клиенты, новые схемы) тоже должна попадать в выборку |
| **Объём** | История операций большая, но по важному классу (подтверждённая схема) — единицы. По эскалациям больше (порядка 400/мес), но это не означает что там подтверждённые схемы. Объём по целевому классу **недостаточен** для обучения с учителем |
| **Качество** | Пропуски, дубли, противоречия в назначении платежа (свободный текст), разные форматы от разных систем. Назначение платежа — это свободный текст и требует дополнительной нормализации и выявления признаков |
| **Право использовать** | Банковская тайна, ПДн клиентов, представителей, поручителей. Правовое основание, договор с обработчиком, регион обработки и хранения данных — идти к комплаенсу, DPO и юристам |
| **Вердикт** | **Разрыв с планом закрытия.** Есть дефицит данных, т.к. нет достаточной разметки подтверждённых схем для обучения с учителем. План: программа сбора (контрольная выборка + разметка финмониторинга по гайдлайну) + постановка без учителя (ранжирование) на первом этапе.<br>Кроме того, пока нет правового основания (это отдельный вопрос к юристам, который можно решать в параллель) |

## Раздел 5. Карточка эксперимента

| Поле | Что фиксируем |
| -- | -- |
| **Где именно теряем** | В приоритизации очереди: текущий отбор по правилам даёт низкую результативность (каждая пятая проверка), крупные суммы обрабатываются приоритетно, а сложные схемы в мелких/средних суммах могут теряться |
| **Гипотеза причины** | Закономерность схемы определяется сочетанием признаков (сумма, контрагент, ОКВЭД, назначение платежа, история), которое не описывается пороговыми правилами, поэтому нужна обучаемая модель ранжирования |
| **Конкурирующие объяснения** | (1) Дело не в модели, а в пропускной способности — аналитики не успевают, и любая приоритизация сможет дать эффект<br>(2) Дело в качестве признаков — например, назначение платежа нужно нормализовать и сделать признаком<br>(3) Дело в смещении отбора — исторические метки не отражают реальную картину |
| **Рычаг** | **Признаки** (нормализация назначения платежа, агрегаты) + **модель** (ранжирование) — начать с этого, т.к. данных недостаточно<br>**Данные** (разметка) — параллельно, как дополнительный рычаг позже |
| **Дешёвый различающий эксперимент** | Взять исторические эскалации, разметить небольшую контрольную выборку экспертами, прогнать ранжирование и сравнить результативность top-N с текущим отбором на этой выборке. Если прирост есть — гипотеза модели подтверждается. Если прироста нет — смотреть пропускную способность и признаки |
| **Ожидаемый эффект** | Рост результативности проверок при том же штате. Предварительно для определенности: с 1-2 до 5-10 подтверждённых из 400 эскалаций |
| **Стоимость проверки** | Время экспертов на разметку контрольной выборки + время ML-команды на пилот + инфраструктура |
| **Критерий остановки** | Результативность top-N не отличается значимо от текущего отбора после устранения технических проблем. Это будет значить, что гипотеза модели не подтверждается, переходим к другим рычагам (пропускная способность, признаки) или к постановке без учителя |
