# ADR-003. Прогноз нагрузки на кол-центр: данные, размещение, модель

Статус: предварительное
Дата: 19.11.2026
Инициатива: №15. Прогнозировать нагрузку на кол-центр для планирования смен

## Контекст

Планирование смен под прогноз нагрузки. Ценность — SLA, меньше переработок/простоев.

Ссылки: паспорт инициативы №15, разделы 1–5; канвас оценки.

## Жёсткие ограничения

- Если в признаки попадают записи звонков — это ПДн/банковская тайна. Это вопрос к DPO и юристам.
- Агрегированные данные о нагрузке — тут ПДн должны быть минимальны, но правовое основание всё равно проверить у юристов и DPO.
- Решение о расписании принимает человек, а не модель.

## Сравнительные критерии

После отсечения по жёстким ограничениям сравниваем по:

- ценность/эффект (SLA, переработки/простои)
- выполнимость (прогноз временного ряда это классическая задача)
- данные (история нагрузки)
- стоимость
- риск (низкий)

## Рассмотренные варианты

### По размещению — пилот и прод

| Вариант | Почему |
| -- | -- |
| Публичный API | Отклонен. Для прогноза не нужен (табличная модель, не LLM). Данные агрегированные, но потенциально чувствительные |
| Существующая инфраструктура банка / своё облако | **Выбран.** Табличная модель прогноза, данные в контуре банка |
| Выделенный контур / on-prem | Возможно. Но зависит от инфраструктуры банка, в общем случае не обязателен |

### По модели

| Вариант | Почему |
| -- | -- |
| Публичный рейтинг / LLM | Отклонён. Прогноз временного ряда это не задача LLM, классическая ML-модель дешевле и точнее |
| Классическая ML-модель прогноза (градиентный бустинг и т.п.) | **Выбран.** Стандарт для временных рядов |
| Простое правило без ML | Отклонён. Если baseline (например вариант "как в прошлую неделю") не достигает целевого MAE/MAPE, то скорее всего простыми правилами будет сложно решить |

## Решение

- **Размещение:** в контуре банка (существующая инфраструктура или своё облако). Тут пилот и прод могут совпадать.
- **Модель:** классическая ML-модель прогноза с baseline (например, "как в прошлую неделю"). LLM не используется.

## Допущения

| Допущение | Источник | Критично для вывода |
| -- | -- | -- |
| История покрывает сезоны и праздники | Проверка ряда | Да |
| MAE/MAPE достижимы на целевом горизонте | Проверяется на пилоте | Да |
| Данные о нагрузке не содержат чувствительных признаков | К DPO | Средне |

## Риски и что с ними делаем

- **Плохой прогноз на праздниках/пиках**: календарные признаки, проверка на отложенном периоде.
- **Разрывы в ряду**: проверка непрерывности. Нужно задокументировать.
- **ПДн**: если используются записи звонков, за ответом о допустимости идти к DPO.

## План выхода

Зависимости от вендора тут нет, модель своя, данные в контуре банка. При росте нагрузки нужно пересматривать инфраструктуру.

## Триггеры пересмотра

- изменение профиля нагрузки (новые каналы, кампании)
- появление новых требований к точности
- провал пилота по MAE/MAPE

## История
