# Паспорт AI-инициативы

Инициатива №2. Распознавание и оцифровка сканов кредитной заявки

## Раздел 2. Постановка

| Поле | Что фиксируем |
| -- | -- |
| **Бизнес-действие** | Андеррайтер получает структурированную карточку полей пакета кредитной заявки вместо ручного переноса. Сокращается время разбора пакета (сейчас около полутора часов) и доля ошибок переноса |
| **Объект и единица решения** | Документ пакета кредитной заявки (справка, выписка, отчётность, договор). Одно решение — по одному документу. Итоговое кредитное решение — по пакету, его принимает андеррайтер |
| **Момент** | **Асинхронно** (документ поступает в пакет, обрабатывается, результат появляется в карточке заявки) + **по запросу** (при разборе на стороне андеррайтера) |
| **Операция** | **Извлечение** нужных сведений (поля) + **распознавание** (сканы) |
| **Модальность** | **Изображение** (PDF-сканы, фото с телефона) + **текст** (выгрузки, Excel) + **документ** (разные форматы от разных бухгалтерских систем) |
| **Выход модели** | Набор полей со ссылкой на источник (страница/блок) и уверенностью распознавания. Для сканов — распознанный текст/структура |
| **Бизнес-выход** | Структурированная карточка пакета для андеррайтера, прошедшая сверку со справочниками и проверку полноты пакета. Отличается от выхода модели: нужна нормализация, сверка и проверка инвариантов. |
| **Источник правильного ответа** | Ручная разметка полей экспертами (андеррайтеры, кредитные аналитики) по гайдлайну. А также эталонные значения из систем банка (справочники, ранее проверенные данные) |
| **Конвейер** | **Распознавание сканов (OCR/CV)** → **извлечение полей (LLM)** → нормализация и сверка со справочниками (код) → проверка полноты и арифметических инвариантов (код) → проверка андеррайтером → кредитное решение (человек) |
| **Альтернативные постановки** | (1) Только распознавание в текст без извлечения полей — меньше ценности, андеррайтер всё равно переносит вручную.<br>(2) Полное автозаполнение кредитного решения — итоговое решение должно оставаться за человеком.<br>(3) Извлечение только обязательных полей на первом этапе, опциональные — позже.<br>**Вопрос бизнесу**: Какие поля обязательны для андеррайтинга, а какие опциональны, и что считается состоянием "пакет собран"? |

## Раздел 3. Оценка качества

| Поле | Что фиксируем |
| -- | -- |
| **Бизнес-метрика** | Время разбора пакета андеррайтером (сейчас около полутора часов) и доля документов, прошедших без ручной правки полей. Вторичная метрика — доля ошибок переноса, которые пришлось исправлять |
| **Положительный класс** | Поле извлечено верно и совпало с эталоном. Для скана — текст распознан с допустимым качеством |
| **Метрика под решение** | **Field-level accuracy / F1** по полям (доля верно извлечённых значений по каждому обязательному полю) + доля документов, прошедших без ручной правки. В этом решении precision/recall по всему документу не годятся, т.к. важна точность по каждому полю отдельно, а не документ целиком |
| **Baseline** | Текущий ручной перенос полей андеррайтером. Сравнение — по времени разбора и доле ручных правок (т.е. ближе к бизнес ценности), а не по точности модели |
| **Проверочная выборка** | Отложенная выборка документов, размеченная экспертами независимо от модели. Должна покрывать разные форматы (Excel, PDF-скан, фото), разные типы документов и разные бухгалтерские системы. Оценка на обучающих документах будет нечестной |
| **Рабочая точка** | Порог уверенности по полю. Если уверенность ниже — поле помечается для ручной проверки и показываются/подсвечивается андеррайтеру |
| **Показатели в этой точке** | Field-level accuracy по обязательным полям, доля документов без ручной правки, доля полей, ушедших на ручную проверку, время разбора пакета |
| **Цена ошибок** | Пропуск/неверное поле — ошибка в кредитном решении, риск для банка (кредитный риск, репутация).<br>Ложная тревога (поле помечено для проверки зря) — время андеррайтера.<br> Пропуск для бизнеса скорее всего дороже лишней проверки. Но надо подтвердить у бизнеса |
| **Guardrails** | (1) Не растёт доля ошибок в кредитных решениях.<br>(2) Не падает качество на редких типах документов.<br>(3) Время разбора пакета не растёт.<br>(4) Доля ручных правок не превышает согласованный порог. |

## Раздел 4. Готовность данных

| Поле | Что фиксируем |
| -- | -- |
| **Решение** | Извлечение полей из документов кредитной заявки для андеррайтера |
| **Объект и гранулярность** | Документ пакета. Запись — один документ. Поля — на уровне одного документа |
| **Источник и владелец** | Документы приходят от клиентов, хранятся в системах банка.<br>Владелец: кредитное подразделение и ИТ-команда банка (по разметке — андеррайтеры/кредитные аналитики) |
| **Источник правильного ответа** | Ручная разметка полей экспертами по гайдлайну. А также эталонные значения из систем банка. Появляется в момент разметки |
| **Доступность признаков в проде** | Все поля документа доступны в момент обработки. Данные андеррайтера (решение по заявке) не должны использоваться как признак — это утечка из будущего |
| **Разметка** | Ручная разметка полей экспертами. Нужно сформировать гайдлайн (что считать верным значением, как нормализовать), оценка согласованности между разметчиками, версионирование гайдлайна |
| **Смещение отбора** | Есть смещение по типам документов и по клиентам (крупные клиенты, значит больше документов определенных форматов). Нужна стратификация выборки |
| **Репрезентативность** | Нужны разные форматы (Excel, PDF-скан, фото), разные типы документов (справки, выписки, отчётность, договоры), разные бухгалтерские системы, редкие форматы. Новая история (новые клиенты, новые формы) должна попадать в выборку |
| **Объём** | Документов много (пакеты по всем кредитным заявкам), но по редким типам и форматам может быть мало. Объём по важным полям и типам документов нужно проверить |
| **Качество** | Пропуски, дубли, противоречия, разные форматы, качество сканов (фото с телефона?). Потребуются разные способы извлечения |
| **Право использовать** | ПДн заёмщиков, поручителей-физлиц; банковская тайна. Правовое основание, договор с обработчиком, регион обработки и хранения — к комплаенсу, DPO и юристам. Автоматизированные решения по ПДн это отдельный вопрос к юристам |
| **Вердикт** | **Можно начинать пилот.** Источник сигнала есть (ручная разметка), качество и объём по основным типам документов достаточны для пилота. Однако редкие форматы нужно добрать. А правовые вопросы закрывать можно по ходу |

## Раздел 5. Карточка эксперимента

| Поле | Что фиксируем |
| -- | -- |
| **Где именно теряем** | На редких типах документов и плохих сканах: извлечение полей ошибается, андеррайтер правит вручную, время разбора пакета не сокращается |
| **Гипотеза причины** | Модель видела мало примеров редких форматов и плохих сканов. Качество распознавания на них ниже, и ошибка тянется в извлечение полей |
| **Конкурирующие объяснения** | (1) Дело не в модели, а в нормализации — разные форматы одного и того же поля.<br>(2) Дело в гайдлайне разметки — эксперты размечают по-разному.<br>(3) Дело в постобработке — сверка со справочником отбрасывает верные значения. |
| **Рычаг** | **Данные** (добрать примеры редких форматов и плохих сканов) + **признаки** (нормализация) — на первом этапе.<br>**Модель** — если рычаг с данными не поможет, можно попробовать улучшить модель |
| **Дешёвый различающий эксперимент** | Взять небольшую выборку редких форматов, разметить, добавить в обучение, проверить на отложенной части. Если прирост есть — гипотеза данных подтверждается. Если прироста нет — смотреть нормализацию и постобработку |
| **Ожидаемый эффект** | Рост field-level accuracy на редких форматах и сокращение доли ручных правок |
| **Стоимость проверки** | Время экспертов на разметку + время ML-команды + инфраструктура |
| **Критерий остановки** | Прирост на редких форматах не значим после добавления данных — гипотеза данных не подтверждается, переходим к нормализации/постобработке |
